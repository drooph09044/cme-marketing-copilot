# ID Graph and Reporting Migration Audit

Audit date: 2026-07-29  
Target application root: `cme-marketing-copilot/Source-Code`
Deployment root: `cme-marketing-copilot`

## 1. Executive Summary

The Karthik Identity Graph enhancements and the latest standalone Reporting implementation have been merged into the maintained Databricks application. The migration preserves the target's Flask composition, Databricks App wrapper, Unity Catalog compatibility layer, data registry, SQL warehouse health behavior, environment-derived AJO credentials, existing authentication routes, and production frontend serving model.

The implementation adds:

- four enhanced identity pipeline stages for matching-field preparation, candidate generation/scoring, guarded clustering, household linking, and golden-record construction;
- governed media and sports identity configuration;
- source-scoped configuration and pipeline-run APIs;
- feature-level match evidence, match tiers, clustering guardrails, separate household relationships, provenance, and richer graph/profile responses;
- identity, customer-profile, data-quality, cleansing/standardization, audience/segment, and campaign/journey reporting APIs and dashboards;
- exact quality calculations and privacy-conscious record drill-downs;
- UC table registrations for the enhanced prepared-record and household-link datasets;
- Volume mappings for config overrides and report/summary artifacts;
- explicit deployment inclusion of reporting contracts and journey definitions.

No standalone AJO token or API key was copied. Existing Databricks secret-backed settings remain authoritative. No live Unity Catalog table was mutated during this migration.

Implementation parity is complete at code and deployment-package level. Production promotion remains gated on a controlled staging run against live UC tables and Volumes because this workstation does not have authority to execute or validate the target workspace data plane.

## 3. ID Graph Change Analysis

### New functionality and processing flow

1. **Enhanced matching-field preparation**
   - Configurable source-field and derived-field names.
   - Email normalization, phone normalization, name tokens/initials/phonetics, address normalization, and configured exact identifiers.
   - Dynamic media and sports schemas are retained rather than flattened.

2. **Candidate generation and feature scoring**
   - Configured blocking strategies and same-source controls.
   - Email, phone, name, address, device/IP probabilistic, and configured extra feature comparison pipelines.
   - Feature confidences, weights, and contributions.
   - Raw and final confidence, matched fields, human-readable techniques, tier classification, and decision reason.

3. **Guarded clustering**
   - Configured identifier priority.
   - Accepted tier controls for exact, strong, medium, and permitted weak edges.
   - Weak-edge matched-field allow lists.
   - Maximum distinct email, phone, and name guardrails.
   - Deterministic cluster and household identifiers.
   - Full-refresh/incremental-mode metadata.

4. **Separate household relationships**
   - Same-address/ZIP relationships are emitted to `household_links`.
   - Household edges do not merge people when exact person identifiers conflict.
   - Household evidence includes address confidence, match fields, techniques, classification, and decision reason.

5. **Golden record construction**
   - Source-aware output column mapping.
   - Most-frequent-value selection with candidate provenance.
   - Multi-valued email, phone, name, and address lineage.
   - Superseded-ID mapping for every member record.
   - Golden and clustering summary artifacts.

### Hidden side effects

- Candidate data is large: 660,069 media and 430,376 sports reference pairs.
- Exact reporting can scan full standardized/candidate datasets; the configured pipeline read ceiling is 1,000,000 rows.
- A full identity run launches four sequential processes with a 900-second limit per stage.
- Media reference data is dominated by weak candidate edges; weak clustering is therefore governed by explicit matched-field patterns and cardinality limits.
- Config updates change future cluster outcomes and are stored as source-scoped overrides in UC mode.
- Household relationships are deliberately secondary and do not merge person clusters.
- The pipeline is full-refresh in the supplied configs; incremental metadata is present but disabled.

### Calculations and aggregation behavior

- Completeness is measured on monitored fields applicable to each source table.
- Validity uses field-specific validation rules.
- Consistency uses configured canonical formats.
- Uniqueness excludes pipeline identifiers and compares exact business-value fingerprints within a source table.
- Accuracy is explicitly `null` because no governed ground-truth accuracy source is available; it is not fabricated.
- Rejected records are preprocessed rows without a corresponding standardized output.
- Unexpected output records are standardized rows absent from preprocessing.
- Customer LTV is exposed only when a governed monetary measure exists. Propensity and monthly proxies are not renamed as LTV.
- Sports realized LTV deduplicates transaction IDs and excludes returned, cancelled, refunded, and voided commerce.
- Reporting distinguishes runtime outcome evidence from static journey-definition/catalog evidence.
- Missing source data returns unavailable/error contracts instead of synthetic completeness claims.

### Filters, datasets, and exports

- All new reporting endpoints are source scoped.
- Quality drill-down supports category, issue type, offset, and limit.
- Identity and customer profile drill-downs are paginated.
- Campaign/journey reports retain date range and filter metadata.
- Existing customer profile export remains available.
- Standardization report JSON is persisted through the configured artifact layer.
- Record-level quality responses omit raw values and return identifiers, issue types, reasons, and fields only.

### UI and routing integration

- Data Overview adds a Data Quality Reporting tab.
- Campaign Manager replaces the old embedded summary with the complete campaign/journey reporting view and context-aware header.
- Existing Customer Profile and ID Graph report tabs now render the new source views.
- Existing application routes and tabs remain in place; no React Router route was removed.
